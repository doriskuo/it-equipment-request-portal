# 資訊設備採購申請系統 (IT Procurement Workflow MVP)

這是一個針對「資訊設備採購申請」實作的 Prototype / MVP，提供基本的線上化簽核與後續處理作業展示。本文件依照測驗交付要求，依序說明系統相關資訊。

## 1. 系統架構／資料結構說明

本專案採用 **Monorepo** 架構，分為前端 (web) 與後端 (api)。

- **前端 (Frontend)**: React 19, Vite, TypeScript, TailwindCSS v4, Zustand
- **後端 (Backend)**: Node.js, NestJS, TypeScript
- **資料庫與 ORM**: MySQL 8.0, Prisma ORM

### 資料結構 (Schema) 簡述
核心資料模型定義於 `apps/api/prisma/schema.prisma`：
- `User` / `UserRole` / `Department`: 實作基本 RBAC (Role-Based Access Control) 權限模型，管理員工、主管、IT 等角色。
- `ProcurementRequest`: 採購申請主檔，紀錄申請人、用途、預估總金額、目前處理節點與狀態。
- `RequestItem`: 採購項目明細，支援單次申請多項設備，並具備獨立的到貨狀態。
- `WorkflowAction`: 處理紀錄 (Audit Trail)，紀錄所有角色的審核、退回等操作時間與備註。

## 2. 安裝及執行方式

### 環境需求
- Node.js (建議 v20 或以上)
- Docker (用於啟動本地 MySQL 資料庫)
- npm

### 初始化與啟動步驟

以下指令皆於**專案根目錄**下執行：

```bash
# 1. 複製環境變數設定檔並可依需求調整 (預設供 docker-compose 使用)
cp .env.example .env

# 2. 啟動資料庫 (MySQL 8.0 運行於 port 3307 以避免與本機環境衝突)
docker-compose up -d

# 3. 安裝相依套件 (根目錄與各子專案)
npm install
cd apps/api && npm install && cd ../..
cd apps/web && npm install && cd ../..

# 4. 建立資料庫結構並匯入測試資料 (Seed)
npx prisma db push
npx prisma db seed

# 5. 啟動前後端開發伺服器 (根目錄一鍵啟動)
npm run dev
# 前端將運行於 http://localhost:5173
# 後端將運行於 http://localhost:3000
```

## 3. 測試帳號／角色及測試方式

為方便評估，系統已建立模擬登入 (Mock Login) 介面。您可透過以下兩種方式無縫切換身份進行測試：
1. **登入頁面**：於系統入口 (`/login`) 直接點選角色卡片登入。
2. **系統內部快速切換**：登入系統後，可隨時點擊畫面上方導覽列 (Header) 的「當前使用者名稱」，透過下拉選單即時轉換角色。這方便您在送出表單後，直接切換為主管或採購進行後續簽核，無須反覆登出登入。

可供測試之角色與對應權限如下：

1. **員工 (emp_alice)**：可建立採購申請、查看自己提出的申請單，並於設備到貨後進行簽收。
2. **部門主管 (mgr_bob)**：負責審核所屬部門員工提出的申請單。
3. **高階主管 (vp_clark)**：負責審核總金額較高 (大於 50,000 元) 的請購單。
4. **IT 人員 (it_diana)**：負責填寫設備技術評估與相容性意見。
5. **採購人員 (proc_eve)**：負責填寫實際供應商、真實採購單價，並可標記設備的交貨狀態。
6. **會計人員 (acc_frank)**：負責核對採購單金額，完成帳務確認與結案。

## 5. 系統邊界定義與需求假設 (System Boundaries & Assumptions)

在開發過程中，基於業務流程分析與真實企業架構的考量，對本專案進行了明確的系統邊界定義與擴充預留：

1. **系統整合邊界 (Integration Boundaries)**：
   經業務流程梳理，本系統專注於「簽核工作流引擎」，並將以下企業模組定義為外部邊界。本專案目前透過資料庫 Seed Data 與 API 模擬方式處理邊界資料交換，以建立未來與真實系統串接的架構基礎：
   - **HR / 組織管理系統**：提供申請人資訊、部門階層與主管層級關聯。
   - **設備主檔管理 (Equipment Master)**：提供標準設備分類、型號與參考價格 (Reference Price)。
   - **採購管理系統 (Procurement)**：提供實際採購金額、供應商與訂單狀態。
   - **會計與財產系統 (Accounting / Asset)**：負責流程末端的帳務核對與資產建立。

2. **設備分批交貨假設**：
   實務上採購多項設備時可能無法同時到貨。為此，系統將「到貨狀態」定義於明細品項層級 (`RequestItem`)，允許申請人針對單一設備進行「部分簽收」，不強制要求整張訂單同時完成。

3. **退回流程 (Return) 假設**：
   退回操作不應直接終止流程，而是將單據退回至「申請人」階段。申請人可修改內容後重新提交，保留原單號與完整的歷史審核軌跡。

4. **通知系統擴充預留 (Email 寄送)**：
   目前各節點的審核通知為求測試便利，僅實作「站內鈴鐺推播」。於後端 `notifications.service.ts` 中，已建立真實 Email 發送的擴充樁 (Stub)，未來可串接外部 SMTP 或 AWS SES 等郵件服務。

5. **動態退回路由 (Dynamic Return Routing) 擴充預留**：
   在真實企業實務中，退回流程可能具有多向性（例如：採購端遇設備停產，需退回給 IT 重新評估替代型號，而非退回給原申請人）。鑑於目前無法確認企業實際的部門規模與權責劃分，本 MVP 採用了「相對簡易且不易出錯」的退回設計：除會計帳務退回外，其餘節點皆預設退回至「申請人」階段。未來系統可擴充「退回原因代碼 (Reason Code)」機制，依據不同代碼動態決定退回的目標節點。
